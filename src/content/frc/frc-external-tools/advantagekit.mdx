<RulesBox title="An architecture, not just a tool">

AdvantageKit is listed among external tools, but adopting it is an architectural decision rather than an add-on. Your robot class changes, your subsystems get structured around the [IO layer](/frc/io-layer), and logging stops being something you remember to do.

That is the trade: more structure up front, in exchange for being able to reproduce any match on a laptop afterwards. This lesson covers the framework; [Hardware Abstraction with IO Layers](/frc/io-layer) covers the subsystem structure it expects, and [Simulation Basics](/frc/simulation-basics) covers replay.

</RulesBox>

### What is AdvantageKit?

AdvantageKit (Team 6328) logs **inputs** to your robot code—sensor readings, buttons, joysticks—during a match. Replay feeds those same values back through unchanged code in simulation so you can debug without the robot on the field.

That differs from logging only outputs you chose ahead of time. Input logging enables [deterministic replay](https://docs.advantagekit.org/data-flow/built-in-logging): the same sensor stream, in the same order, as on the field.

Docs: [AdvantageKit](https://docs.advantagekit.org/) | [GitHub](https://github.com/Mechanical-Advantage/AdvantageKit)

### How It Works

Subsystems use the [IO layer pattern](https://docs.advantagekit.org/data-flow/recording-inputs/io-interfaces/): an interface swapped for real hardware, simulation, or a log reader. On the robot, implementations read hardware and inputs are logged. In replay, implementations read the log and your subsystem logic stays the same.

### LoggedRobot

The robot class extends `LoggedRobot` instead of `TimedRobot`:

```java
public class Robot extends LoggedRobot {
    private Command autonomousCommand;
    private RobotContainer robotContainer;
```

It is a drop-in replacement — same `robotPeriodic`, same `autonomousInit`, same 20 ms loop. The difference is that loop timing is handed to the logger, which is what makes replay possible: in replay mode the loop runs as fast as the log can be read rather than in real time.

Setup happens in the constructor, before anything else exists:

```java
public Robot() {
    // Record metadata — stamped into every log
    Logger.recordMetadata("ProjectName", BuildConstants.MAVEN_NAME);
    Logger.recordMetadata("BuildDate", BuildConstants.BUILD_DATE);
    Logger.recordMetadata("GitSHA", BuildConstants.GIT_SHA);
    Logger.recordMetadata("GitBranch", BuildConstants.GIT_BRANCH);
    Logger.recordMetadata(
        "GitDirty",
        switch (BuildConstants.DIRTY) {
            case 0 -> "All changes committed";
            case 1 -> "Uncommitted changes";
            default -> "Unknown";
        });

    switch (Constants.currentMode) {
        case REAL:
            // Log to a USB stick ("/U/logs") and publish live
            Logger.addDataReceiver(new WPILOGWriter());
            Logger.addDataReceiver(new NT4Publisher());
            break;
        case SIM:
            Logger.addDataReceiver(new NT4Publisher());
            break;
        case REPLAY:
            setUseTiming(false); // Run as fast as possible
            String logPath = LogFileUtil.findReplayLog();
            Logger.setReplaySource(new WPILOGReader(logPath));
            Logger.addDataReceiver(new WPILOGWriter(LogFileUtil.addPathSuffix(logPath, "_sim")));
            break;
    }

    Logger.start();

    robotContainer = new RobotContainer();
}
```

`BuildConstants` is generated by the build, not written by hand. It stamps the git commit, branch, and whether the working tree was dirty into every log file.

<RulesBox title="Why the metadata matters">

When a log shows behaviour nobody can explain, the first question is always "what code was actually on the robot?"

`GitSHA` answers it exactly, and `GitDirty` answers whether the code on the robot corresponded to a commit at all. Check both before spending an hour analysing a log.

Also: **plug in the USB stick.** On a real robot `WPILOGWriter` writes to `/U/logs`. No stick, no log, and the post-match analysis you were counting on does not exist.

</RulesBox>

### AdvantageKit Subsystem Structure

```java
public class Flywheel extends SubsystemBase {
    // 1. Define the inputs that will be logged
    // API: @AutoLog annotation - https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/AutoLog.html
    @AutoLog
    public static class FlywheelInputs {
        public double velocityRadPerSec = 0.0;
        public double appliedVolts = 0.0;
        public double currentAmps = 0.0;
    }

    // 2. Define the IO Interface
    public interface FlywheelIO {
        default void updateInputs(FlywheelInputs inputs) {}
        default void setVoltage(double volts) {}
    }

    private final FlywheelIO io;
    private final FlywheelInputsAutoLogged inputs = new FlywheelInputsAutoLogged();

    // Constructor injects the implementation (Real, Sim, or Replay)
    public Flywheel(FlywheelIO io) {
        this.io = io;
    }

    @Override
    public void periodic() {
        // 3. Update inputs from the IO layer
        io.updateInputs(inputs);
        
        // 4. Log the inputs automatically
        // API: Logger.processInputs() - https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/Logger.html#processInputs(java.lang.String,java.lang.Object)
        Logger.processInputs("Flywheel", inputs);

        // Your logic uses 'inputs.velocityRadPerSec' instead of 'motor.getVelocity()'
    }

    public void runVolts(double volts) {
        io.setVoltage(volts);
    }
}
```

### Logging

[@AutoLog](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/AutoLog.html) on an inputs class logs every field each loop (WPILOG/RLOG). ([Logging docs](https://docs.advantagekit.org/getting-started/what-is-advantagekit/example-output-logging/))

Log computed values with [Logger.recordOutput()](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/Logger.html#recordOutput(java.lang.String,java.lang.Object)):

`Logger.recordOutput("MyState/Target", targetValue);`

`Logger.recordOutput("Odometry/Pose", pose);`

### Inputs vs Outputs

There are three logging mechanisms and they are easy to confuse:

<ContentTable
  headers={["Mechanism", "Recorded as", "Used for"]}
  rows={[
    ["<code>@AutoLog</code> on an inputs class", "<strong>Input</strong>", "Anything read from hardware &mdash; makes replay possible"],
    ["<code>@AutoLogOutput</code> on a method", "<strong>Output</strong>", "Values your code computed or commanded"],
    ["<code>Logger.recordOutput(key, value)</code>", "<strong>Output</strong>", "One-off values from inside a command"]
  ]}
/>

The distinction is the whole trick. **Inputs are replayed back into the code; outputs are what the code produced.** If a sensor reading is recorded as an output, replay will not feed it back in, and the replay is meaningless.

```java
// input — read from hardware, replayed
io.updateInputs(inputs);
Logger.processInputs("Drive/Module0", inputs);

// output — computed by us, not replayed
Logger.recordOutput("Odometry/Trajectory", activePath.toArray(new Pose2d[0]));
```

### Log Replay

Replay loads a match log and runs your code against recorded inputs. Step through logic, change code, and check fixes against real data. With deterministic robot code, replay matches field behavior.

[Log replay documentation](https://docs.advantagekit.org/data-flow/built-in-logging)

<RulesBox title="Getting Started" subtitle="Best practices:">

- Use the [IO Layer pattern](https://docs.advantagekit.org/data-flow/recording-inputs/io-interfaces/) for all subsystems that interact with hardware.
- Log all inputs using [@AutoLog](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/AutoLog.html) annotations.
- Log important outputs and states using [Logger.recordOutput()](https://docs.advantagekit.org/javadoc/org/littletonrobotics/junction/Logger.html#recordOutput(java.lang.String,java.lang.Object)).
- Keep input classes simple: use primitives and basic data structures.
- Use [AdvantageScope](https://docs.advantagescope.org) to visualize and analyze log files.
- Keep your code deterministic: avoid random numbers, timestamps, or other non-deterministic sources in logic.

</RulesBox>

### @AutoLogOutput

Not every subsystem needs a full IO layer. For a simple mechanism, `@AutoLogOutput` logs the return value of a method with no other setup:

```java
@AutoLogOutput(key = "Conveyor/velocity")
public double getConveyorVelocity() {
    return conveyor.getVelocity().getValueAsDouble();
}
```

Because the annotation logs a **return value**, write setters that return the value they set. That is what puts commanded values in the log alongside measured ones, with no extra logging code anywhere:

```java
@AutoLogOutput(key = "Intake/targetPos")
public double setIntakePosition(double pos) {
    pivot.setControl(motionMagic.withPosition(pos));
    return pos;
}
```

Now `Intake/targetPos` and `Intake/Position` — commanded and actual — can be dragged onto the same graph. A `void` setter would leave half of that picture missing.

Remember these are **outputs**: visible in AdvantageScope, but not fed back in during replay. Anything read from hardware that your logic depends on belongs in an `@AutoLog` inputs class instead.
